| F88 | Item handoff | §2.4, §13 | — | shipped | `dudes do <ITEM> -slice <file.json> [-base <ref>]`, run from the dev repo's root with the role's slicing, prepares one slice of an item from the repo's tracked `dudes/` folder: `profile.json`, `specset.json` (each root a repo path relative to the dev repo and its pin, a release branch or a tag) and `config.json` (worker, gate image, formatter; no workspace). A repo of several products keeps a folder per product beside the shared `dudes/config.json`: `dudes/<product>/` with that product's `profile.json` and `specset.json` (its roots pinned at the product's own release) and an optional `config.json` over the shared one; the folder is the product. The item's ID finds its product: the one whose profile gives its backlog that ID (the owner of the ID family). An item no product claims, or more than one, fails before anything is made and names the products the repo knows, each with its ID family. The model host is the machine's, never the repo's: `DUDES_OLLAMA_URL`, else the user's own `dudes.json`, else the `OLLAMA_API_BASE` Aider reads; none set fails before anything is made. It creates the worktree `.worktrees/<id>` on `feature/<id>` from `-base` (default: the upstream of the current branch, else HEAD; it refuses when either exists), pins each spec root as a detached worktree `<root repo>/.worktrees/spec-<id>`, writes the worktree's `.dudes/`, starts the run on a commit of its own (its notes then stay off a base commit that other worktrees share), runs init and freeze, and prints the next command; a failure takes the worktrees back. The contract narrows the item to the slicing's criteria and holds a red-test task (`expect: fail`, `approval: after`, writable: the tests and hooks) and a code task (`approval: after`, writable: the scope minus those files, by `!` patterns, F78), titles with facts only. Acceptance tests sit where the language needs them: the contract names them (`tests`), the run starts at implementation with no placeholder under `tests/`, and the coverage gate, the worker's test files and the evidence rows count them. The review loop: when a task ran and waits for approval (`approval: after`), `dudes status` and `status -json` carry its review packet — the task's diff of its writable paths since it first ran (`task_base` in the run state) with its commits; the gate run on HEAD with the tests that passed, failed and skipped (its log and the acceptance rerun); the worker's last reply (`.dudes/replies/<task>.md`, its code blocks shortened to their length) — each cut to a bound, naming the git command or file that holds the whole. `dudes decide` and `dudes redo` record who answered, in their event and in the run state's note (`decided_by`): the git identity, and the role `-by <role>` names; an agent shares its human's identity, so only the role tells a role-play reviewer's answer from the human's or DevOps'. Every worker call a step makes — the code worker in implementation, the text worker in a text phase — is a `worker` event with its local tokens — Ollama's own counts for the text worker, the sum of Aider's `Tokens:` reports for the code worker (rounded as Aider prints them; Pi reports none) — and its duration; `dudes test -fix` and `dudes do -pick` record none. The ledger — those `worker` events and every `decide` and `redo` with who answered and why — lives in git as well: a line each in the note under `refs/notes/dudes/ledger` on the commit HEAD was on. A notes ref is one for every worktree of a repository, so the ledger outlives the slice's worktree and branch; `dudes events` reads it from there when `.dudes/events.jsonl` is not in the workspace (a dev repo's root, once the slice's worktree is gone). The engine's commits on the item branch name the slice, the task and the pass, with the role tag and the `Item:` and `Task:` trailers: `test(BK-001a): red tests for AC-1 and AC-3, pass 2 [🔹engine]`, `feat(BK-001a): code for AC-1 and AC-3, pass 1 [🔹engine]`, the guard's `revert(BK-001a): pass 3 of the code for AC-1 and AC-3 broke …` (F86); the first commit, `chore(BK-001a): start the run for AC-1 and AC-3 of BK-001`, says that it anchors the run's notes and names the pins. `dudes decide` on a finished task lands it as one commit, `feat(BK-001a): code for AC-1 and AC-3 [🔹engine]` with a `Passes:` trailer: its failed passes, the guard's reverts and its redos are what a reviewer would squash. The squash runs through `git commit` and its hooks and copies the notes of the task's last commit (gate run, acceptance run, run state) to the new one; a commit another branch or a remote holds, or a staged change, leaves the commits as they are and says so, and a squash that fails after its commit keeps the passes' ref and names what is missing. A pause holds until its own task is answered: a decide or redo of another task is recorded and changes nothing else, a task that ran and still waits for its review pauses again before any later task runs, and a slice never leaves implementation. The passes stay the record: before the squash the task's old head is kept under `refs/dudes/passes/<slice>/<task>/<n>`, one ref per landing, a local ref that neither `git push` nor a clone takes by default — the failed passes, the redos and the reverts stay in the repo, their notes on commits that exist, the ledger's lines among them (never copied, so never counted twice). The slice ends with its last task: the approval that leaves no task open saves the run state as `ended`, `step` and `run` then name the merge instead of entering QA, whose QR is the spec repo's, and a redo opens the slice again. After the merge the newest run note on the dev branch reads `ended`, so `dudes status` there shows no run under way and intake (F84) binds the next item. A stub writes nothing outside a task's scope. So landing the branch, `git merge --no-ff feature/<id>` under the framework's hooks, brings in the product's files and three commits: the start, which anchors the run's notes (the spec freeze, the run's first state), the tests and the code. `dudes land <slice> -by <role>`, run from the dev repo's root once the slice's run ended, makes that merge with the role's tag and the item's trailer — a merge git stops (a conflict, a hook) is taken back — and then removes the slice's spec pins, worktree and merged branch; its run notes and kept passes stay. It refuses before the merge, naming the files, when the worktree or a pin holds a change no commit has. At a worker's escalation `dudes status` shows its question and the answer command; `make approve … WHY=<answer>` answers it. The role-play reaches the engine through make goals, not rule prose: the framework's `make/bridge.mk`, which a dev repo includes by its path, never a copy (`-include`, so a checkout without the framework still runs its own goals), names one engine command per goal, two at most — `make slice ITEM= SLICING=` (`dudes do -slice … -run`: prepare, then run to the first pause), `make review SLICE=` (the run and its review packet), `make approve` and `make redo SLICE= TASK= ROLE= [WHY=]` (decide or redo `-by` the role, then run to the next pause) and `make land SLICE= ROLE=`; the words reach the shell as exported variables, quoted where used, so no text in them is parsed as shell. The first real item (a backup verification in one Go package, 2026-10-14) took 20 hand steps and 418k cloud tokens to prepare and land without it (`TREND.md` §1.1). | Parked on 2026-10-16 with the worlds split (`ROADMAP.md`): `make/bridge.mk` and the role-play handing items over stay in the repo, unused by the role-play; the engine commands serve the local track.
| F89 | Verifiable seal | §4, §10 | — | shipped | The seal is the human's, provably. `dudes seal` signs the seal tag (`git tag -s`) when the sealer's git can sign — `user.signingkey` set, with `gpg.format` openpgp, ssh or x509 (or `tag.gpgSign` on) — and otherwise makes the annotated tag as before and says `unsigned: set user.signingkey to sign seals`; a key that is set but cannot sign stops the seal and takes the seal commit back. The seal commit carries `Sealed-by: <user.name> <<user.email>>`, git's committer identity. `seal.require_signature` in `dudes.json` (default false; a repository's `dudes/config.json` may switch it on, never off) refuses a seal that git is not set up to sign, before any file, commit or tag is made; a setup that is there but fails at signing is the case above. The seal is all or nothing: if the state or the tag cannot be saved after the seal commit, the commit is taken back, and a seal tag name that is taken is refused up front. `dudes verify [tag]` (default: the newest tag reachable from HEAD that points at a seal commit; name another to check it) checks from git alone and exits 0 only when all four hold: `git tag -v` accepts the signature (gpg's keyring, or `gpg.ssh.allowedSignersFile` for SSH keys: who is trusted is the verifying git's setting), the tag points at the `chore(phase): seal [🔹human]` commit, that commit has the `Sealed-by` trailer, and the run's state note on it says sealed — the engine's record, not signed like the tag, read from the notes history once the next run or a reset has replaced the note. **Workers cannot seal:** `dudes seal` works only at `human_decision`, a phase no worker step runs in; Aider is started with `--no-suggest-shell-commands` (no shell command from the model's reply runs) and no test or lint command of its own, and its container holds Aider and git only — no `dudes` binary, no signing key (only the repository is mounted); tests in `internal/aider` pin both. The optional Pi worker (F55) is the exception: it runs on the host with Pi's own tools, a shell among them unless the recipe's `tools` leaves it out — it still cannot seal at the gate, and a tag it makes by hand fails `dudes verify` without the sealer's key. The signature proves the key, not the person: a key kept unlocked in an agent is usable by whatever runs in that shell; a key that needs the human (a passphrase prompt, a hardware key's touch) is not. Three outside reviewers (2026-10-15) sealed from a plain shell: "sign it or stop calling it one". |
