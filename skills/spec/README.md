# Spec-level skills

For the spec repos: product and project specification — PM, UX, security. No model is trained on how DUDES specifies (`CORE.md` §5, *Where skills earn their place*), so the skills here carry that method. They share this background instead of repeating it:

- **The spec-set** is the instance's original documents under named roots; DUDES reads them and never renames them. Each document answers one question, and on a conflict the higher one wins: the document contract of `skills/lead/README.md`, which both levels share.
- **Every requirement and scenario has an ID** that tests, the QR and commits carry; a statement without an ID is not a requirement.
- **A frozen spec is the contract** a dev run implements; a change after the freeze is a new freeze, never an edit under a running item.
- **The gate is the consistency check:** IDs resolve to their owner document, and the backlog, QR and specs agree. The PM checks it by reading and searching the IDs; where the engine is installed, `dudes item check` does it. The PM runs the sweep before the freeze commit and freezes only with zero open findings (`rules/DUDES.md` §6); where the framework clone is built or `dudes` is on PATH, and the repo has the engine's profile (`.dudes/profile.json`), `hooks/commit-msg` refuses a PM commit of spec documents while findings are open.
- **Scope enters top-down.** The release it belongs to exists first, then the spec delta in the owner documents (the requirement, the contracts, the QR rows), then the work item that references them. A contract found while building is reported by the builder (`CONTRACT:`, `work-item`); the PM puts it into its owner document first and the item references it; never into the item alone. The consistency check catches the shortcuts (an item whose release is no milestone, a fact defined twice); the order of the steps is the PM's judgement.
- **A change ripples in the same commit.** A change to an owner document reaches every document that references it in that commit, and the why goes in the commit message, never into a change note in the document (`hooks/pre-commit` refuses a new one). What did not ripple, the consistency check finds as a dangling reference or a missing QR row.
- **Git holds the metadata.** A spec document carries no field for its own version, date, author or status: the commit is the version, `git log` the date, the role tag the author, the branch the status (`development` living, `release/*` frozen). A reference names a file and an ID, never a version. Nothing refuses such a field yet; a pre-commit line beside the change-note rule could.
- **The company's own conventions** — document names, ID families, review rules — live in the instance's spec repo (`AGENTS.md`, its own `skills/`), not here.

Which role loads which skill in the role-play: `rules/DUDES.md` §1. This background grows with the method; when a spec skill repeats a rule, the rule belongs here.
