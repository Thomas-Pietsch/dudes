## What the lanes hold to

- **The worlds are split.** `R` runs in Cursor and Claude Code on its own. Nothing in its rules, skills, templates or setup docs requires the engine: they may name `dudes item check` for where it is installed, a hook may use the engine where it finds it installed, and every rule holds by discipline without it. `E` runs on the model host against its own bench. The bridge is parked: F88's `make/bridge.mk` (slice, review, approve, redo, land) and the role-play handing items to the engine. The file and the engine's commands stay. Unparking it is a step-back decision, not before `E1` passes. A framework change that slows or breaks an instance's run is still erosion; the run's need enters as a source (`CORE.md` §15). No work and no design on the bridge or on handing items between the worlds before `E1` passes (the human, 2026-10-18).
- **In `E` the mechanisms are the cage, not the context.** A worker gets the task, its goals and the output contract (`CORE.md` §2.4). When a model falls short, the stage waits for a better model or changes a mechanism (the slicing, a gate, a setting). It never grows the worker's prompt. A model's reaction to the harness comes before any question of quality or speed: `make bench-smoke` first, one setting changed at a time, a series only with the settings the smoke passed with (`skills/framework/bench`).
- **`E1`'s supply is the bench's own product.** `bench/workspace` is a small Go product with its own spec-set, grown one item per ladder level by DevOps: from `L4` on each item has approved read-only acceptance tests, a reference solution and a hidden test (`L1`–`L3` have the hidden test alone), carries the details real items fail on, and names no instance. A rung is calibrated before the next: one configuration passes it and one fails it; a rung every configuration passes or none does measures nothing and is reworked. Its outcome is clear and repeatable, so models are compared on the same task and the engine's own mechanisms are measured where they fail. A sealed real item of `R` may still become a replay level in the instance that owns it (two exist, local, under the CEO's exception of 2026-10-14); they are the hard comparison, not the gate. No real item goes through the engine while the bridge is parked.
- **`E1`'s case is measured, not assumed.** A pass needs no cloud model, so its cost is local minutes on the model host, recorded per run in the bench record. The ledger against a role-play control run is parked with the bridge.
- **The bench follows the stages.** The engine's regression tests are its Go tests and the stub lifecycle (`make ci`, `make bench`). The ladder's rungs are `E1`'s exit check; the replay levels are comparison levels; neither is a regression test: three runs place a configuration, they do not attribute an engine change. A series runs only for a configuration that passed its smoke (a new model, a changed setting, a new harness) or a new level, on the human's go, and a repeated result ends it. `L1`–`L3` are saturated (every `L3` run passed since engine `9dc0fa6`, 2026-10-12): they only show the pipeline works. A level cut to one slice, starting from the reference state of the slices before it, stops one slice's failure from hiding the next.
- **The order may change.** The stages run dev, then spec, then lead, because models are trained hardest on code and tests settle it (`CORE.md` §2.4). When the world moves, the step back is where the order changes.

## Horizon

Direction, not a stage. Today DUDES is a local-model ADE for one product lifecycle. The human still seals the outcome.

**Where it goes.** An agentic company environment: the same engine, still local, doing the repeated work of the company and not only one increment. It keeps running. You see what is actually in progress, and you instruct it by voice or by text.

Text stays the spec. It is the precise contract. A picture is the dense view — shape, color, and status together — for a person watching the run, and maybe for a worker when one image replaces a long dump. Whether that saves tokens is something to measure. It is not a reason to drop the spec.

**What we rely on.** Git is the database. The engine is IDE-independent and OS-independent: no editor tree and no host vendor is the product. Today the doing still sits in Claude and Cursor, and the UI is text and prompting. Workers take over pieces of that work, lane `E`. The backend we are moving toward is a local process in the DUDES way: Go, a local model, Git as the record.

**What we do not build now.** The face that speaks, understands what the company needs, and shows monitors of the running work. Open-source desks are candidates, not a guarantee that a compatible face will arrive. Do not schedule one without evidence of an unmet need and human adoption; reassess when a desk can operate over DUDES's record without owning the lifecycle. Nor does DUDES become a personal assistant: "it keeps running" means a trigger starts bounded runs with state in Git; an assistant is at most the face. An OS or appliance around DUDES is a deployment choice, not DUDES.

**How a pattern is built.** Simplest fit first: shell, then git, then make and Docker, then Go or an existing tool — the pillars in `CORE.md` §11. The phase machine stays Go. Git as database: `CORE.md` §10. Workers get the task and their goals, nothing else: `CORE.md` §2.4. An instance's product toolchain (for example a CI container) is the instance's choice (`CORE.md` §13).
